# ADR-0004: 메시지 브로커 선정 (Kafka vs RabbitMQ) 및 토픽 분리 전략

## 상태 (Status)
Accepted

## 배경 (Context)
`event_storming.md`에서 Message Broker를 거치는 두 가지 서로 다른 트래픽이 확인됐다.

1. **서비스 간 이벤트 팬아웃** — Streaming이 발행하는 `방송_시작됨`/`방송_종료됨`을 Channel·Chat·Notification 3개 서비스가 각자 독립적으로 구독. 빈도는 매우 낮음(방송 시작/종료 시점당 1회)이지만 유실 시 알림 누락·캐시 미갱신 등으로 이어져 **전달 보장이 중요**.
2. **채팅 메시지 배치 저장** — Chat 서비스가 브로드캐스팅과 영속화를 분리하기 위해 채택한 패턴([ADR-0003](0003-chat-service-framework-selection.md) 논의 과정에서 확정). 빈도가 매우 높고(초당 수천~수만 건) 이미 "optional 영속화"로 정의되어 있어 **유실보다 처리량이 우선**.

이 두 트래픽을 하나의 큐/토픽에서 같이 처리하면, 채팅 폭주 시 이벤트 처리가 지연되거나 반대로 이벤트 컨슈머의 지연이 채팅 처리량에 영향을 주는 문제가 생긴다. 따라서 **브로커 선택**과 **토픽/큐 분리 전략**을 함께 정리한다.

## 검토한 대안 (Alternatives)

| 항목 | Kafka | RabbitMQ |
|---|---|---|
| 처리량 | 파티션 기반으로 수평 확장, 초당 수만~수십만 건 처리에 강점 | 상대적으로 낮음. 클러스터링으로 확장 가능하나 고처리량 로그성 데이터에는 설계 목적상 불리 |
| 팬아웃(다중 구독) | 토픽 하나를 여러 컨슈머 그룹이 각자 독립 오프셋으로 구독 — Pub/Sub이 네이티브 모델 | Fanout Exchange로 여러 큐에 복제해야 함 — 가능은 하지만 Kafka만큼 자연스러운 1등 시민 기능은 아님 |
| 순서 보장 | 파티션 단위로 보장 (파티션 키로 세밀 제어 가능 — 예: 채팅방 ID를 키로 쓰면 방별 순서 보장) | 큐 단위로 보장, 파티션 개념 없음 |
| 재처리/복구 | 로그 기반 저장이라 retention 기간 내 재생 가능 | 컨슈머가 처리한 메시지는 기본적으로 사라짐 (재처리 용이성 낮음) |
| 지연(latency) | 배치/처리량 지향이라 RabbitMQ보다 약간 불리할 수 있음 | 메시지당 지연이 낮은 전통적 큐 시맨틱에 강점 |
| 운영 복잡도 | 파티션/컨슈머 그룹 등 개념이 많아 학습 곡선 있음 | 상대적으로 단순 |

## 결정 (Decision)
**Kafka**를 단일 브로커로 채택한다. 물리적으로 하나의 클러스터만 운영하되, 트래픽 특성이 다른 두 워크로드를 **토픽으로 논리적 분리**한다.

| 토픽 | 용도 | 파티션 전략 | 컨슈머 그룹 |
|---|---|---|---|
| `broadcast-events` | 방송_시작됨/방송_종료됨 등 도메인 이벤트 | 파티션 소수, 전달 보장 우선 | Channel, Chat, Notification — 각각 독립된 컨슈머 그룹으로 동일 토픽을 구독 |
| `chat-message-log` | 채팅 메시지 배치 저장용 버퍼 | 채팅방 ID를 파티션 키로 사용 (방별 순서만 보장, 처리량 우선) | 배치 저장 워커 전용 컨슈머 그룹 (위 그룹과 완전 분리) |

## 근거 (Rationale)
1. **Pub/Sub 네이티브 지원**이 이벤트 팬아웃 요구(3개 서비스가 같은 이벤트를 각자 구독)에 정확히 맞는다 — RabbitMQ의 Fanout Exchange보다 컨슈머 그룹 모델이 더 자연스럽다.
2. **채팅 메시지 배치 저장**이라는 고처리량 로그성 워크로드는 Kafka가 원래 설계된 목적(높은 처리량의 로그 스트림)과 정확히 일치한다. RabbitMQ로 이 정도 처리량을 감당하려면 더 많은 튜닝이 필요하다.
3. 브로커를 물리적으로 2종류(예: 이벤트는 RabbitMQ, 채팅 로그는 Kafka) 운영하는 방안도 검토했으나, 트래픽 특성이 다르다고 해서 반드시 별도 브로커가 필요한 정도는 아니라고 판단했다 — 토픽 분리만으로 컨슈머 그룹이 완전히 격리되어 한쪽 컨슈머 랙이 다른 쪽에 영향을 주지 않으며, 브로커 하나만 운영하는 편이 `.clauderules`의 인프라 최소화 원칙에도 부합한다.
4. 파티션 키를 채팅방 ID로 두면 "방별 순서만 보장하면 충분하다"는 요구사항을 정확히 만족시키면서 파티션을 늘려 처리량을 수평 확장할 수 있다.

## 결과 (Consequences)
* `system_architecture.md`, `tech_stack.md`의 "Message Broker(미확정)" 표기를 Kafka로 갱신한다.
* 향후 실제 구현 단계에서 두 토픽의 retention 정책은 다르게 가져가야 한다 — `broadcast-events`는 짧은 retention도 무방(실시간 처리 후 불필요), `chat-message-log`는 배치 워커가 지연되는 경우를 대비해 최소한의 버퍼 기간 확보 필요.
* Kafka 운영 복잡도(파티션/컨슈머 그룹 관리)는 학습 비용으로 감수한다 — 포트폴리오 관점에서도 "왜 Kafka인가"를 트래픽 특성 기준으로 설명할 수 있는 근거가 된다.
