# ADR-0003: Chat 서비스 프레임워크 선정

## 상태 (Status)
🟡 검토 중 (Open) — **최종 선택 보류**. 아래 3가지 대안과 각각의 장단점/완화책만 정리하고, 채택 여부는 이후 결정한다.

## 배경 (Context)
`event_storming.md`/`system_architecture.md`에서 확인했듯 Chat 서비스는 이 프로젝트에서 트래픽 부하가 가장 크게 걸리는 지점 중 하나다. 특히 두 축의 부하를 구분해야 한다.

1. **영속화 결합 문제** — 메시지 저장을 동기 RDBMS 쓰기로 처리하면 브로드캐스팅까지 지연되는 문제. → 이미 별도 결론으로 **MQ 버퍼링 + 배치 저장** 패턴을 채택하기로 함 (프레임워크 선택과 무관하게 해결됨).
2. **커넥션 동시성 / 팬아웃 문제** — 수십만 동시 접속, 단일 채팅방 10만 명, 월드컵 결승전급 초고빈도 메시지 상황에서 "메시지 1건 → 방 안 전원에게 전송"이라는 쓰기 시점 팬아웃(Fan-out on Write) 자체의 부하. 이 ADR은 **2번 문제에 대한 프레임워크/런타임 선택**을 다룬다.

## 검토한 대안 (Alternatives)

### 옵션 A. Spring Boot (서블릿 스택, Tomcat)

| 구분 | 내용 |
|---|---|
| **장점** | 기존 스택과 완전히 동일 — Eureka/Gateway/MQ/JWT 연동에 추가 작업 없음. 1인 개발 기준 학습곡선 없이 바로 생산성 유지. 이미 확정된 MQ 배치 저장 패턴과 자연스럽게 결합됨 |
| **단점** | 스레드 기반 모델이라 대량 커넥션+팬아웃에 구조적으로 불리. 브로드캐스트를 동기 for-loop로 구현하면 slow consumer 하나가 전체 전송을 지연시키고, 메시지 빈도가 높아지면 워커 스레드 풀이 병목 |
| **완화책** | ① 세션별 전송을 비동기(Async Remote)로 처리 + bounded 아웃바운드 큐(가득 차면 느린 클라이언트 drop/disconnect) ② 메시지 배치/코얼레싱(짧은 윈도우로 묶어 1프레임 전송) ③ 직렬화 1회 후 버퍼 재사용 ④ 방 단위 샤딩(Redis Pub/Sub 채널 + consistent hashing) ⑤ 수평 확장(Eureka 기반, 이미 설계에 있음) |
| **잔여 리스크** | 완화책을 다 적용해도 스레드 기반이라는 구조적 한계는 남음 — 매우 극단적인 트래픽(월드컵 결승전급)에서는 여전히 다른 옵션 대비 불리 |

### 옵션 B. Spring Boot WebFlux (Reactor Netty)

| 구분 | 내용 |
|---|---|
| **장점** | 이벤트루프 기반 논블로킹 I/O로 대량 동시 커넥션 처리에 구조적으로 유리. Redis Pub/Sub(Lettuce reactive)과 자연스럽게 결합. **Java/Kotlin 생태계를 유지**하므로 Eureka/Spring Cloud Gateway/MQ 연동에 이질감이 없음 (옵션 C 대비 통합 비용이 훨씬 낮음) |
| **단점** | 리액티브 스트림 특유의 학습곡선(Mono/Flux, 백프레셔, 디버깅 난이도). 1인 개발 기준 일시적 생산성 저하 가능. JDBC 같은 블로킹 라이브러리가 섞이면 이벤트루프 자체가 블로킹되어 오히려 역효과 |
| **완화책** | 학습곡선은 Spring 공식 진영이라 레퍼런스/문서가 풍부해 상대적으로 완화 가능. DB 접근이 필요하면 R2DBC 사용하거나, 불가피하게 블로킹 호출이 필요한 부분만 `Schedulers.boundedElastic()`으로 격리 |
| **잔여 리스크** | 팀(1인) 숙련도에 따라 초기 구현 속도가 늦어질 수 있음 |

### 옵션 C. Node.js (NestJS / Express + Socket.io 등)

| 구분 | 내용 |
|---|---|
| **장점** | 이벤트루프 네이티브라 대량 WS 커넥션 처리에 강점, Socket.io 등 실시간 채팅에 특화된 생태계와 실전 사례가 많음. MQ(kafkajs/amqplib), Redis(ioredis), JWT(jsonwebtoken) 연동 자체는 어렵지 않음 |
| **단점** | **폴리글랏 도입 비용** — Eureka 공식 클라이언트가 없어 `eureka-js-client` 등 커뮤니티 패키지로 헬스체크/하트비트/graceful deregister를 수동 구현해야 함. 빌드·배포 파이프라인 이원화(JVM 이미지 vs Node 이미지), 관측성 포맷 불일치(Actuator 없음 → `prom-client`로 별도 구현 필요). 1인 개발 기준 유지보수 컨텍스트 스위칭 비용 증가 |
| **완화책** | Eureka 연동 대신 Gateway에 정적 라우트로 등록해 디스커버리 비용을 낮출 수 있으나, 이 경우 "수평 확장되는 서비스의 동적 인스턴스 탐색"이라는 Eureka 도입 취지 일부를 포기하게 됨. 관측성 포맷 불일치는 Observability 자체가 현재 MVP 스코프 밖이라 당장은 영향 없음 |
| **잔여 리스크** | 서비스 1개만 다른 런타임/툴체인을 쓰게 되어, 포트폴리오 서사가 "Java/Spring MSA"에서 "의도적 폴리글랏 MSA"로 바뀜 — 이걸 의도적 강점으로 설명할 수 있는지가 관건 |

## 비교 요약

| 기준 | A. Spring Boot | B. WebFlux | C. Node.js |
|---|---|---|---|
| 대량 커넥션/팬아웃 구조적 적합성 | 낮음 (완화책 필요) | 높음 | 높음 |
| 기존 인프라(Eureka/Gateway/MQ) 통합 비용 | 없음 | 없음 | 있음 (Eureka가 특히 큼) |
| 1인 개발 학습곡선 | 없음 | 중간 | 중간~높음 (+ 운영 이원화) |
| 포트폴리오 서사 | "일관된 Spring MSA" | "일관된 Spring MSA + 리액티브 역량" | "의도적 폴리글랏 MSA" |

## 결정 (Decision)
**보류.** 최종 프레임워크는 아직 선택하지 않는다. 아래 기준이 정리되면 재논의한다.

* 이 프로젝트의 강조점이 "Java/Spring 생태계 내에서의 대규모 트래픽 처리 역량"인지, "언어 경계를 넘는 폴리글랏 아키텍처 설계 역량"인지
* 실제 부하 테스트(가상 사용자 시뮬레이션 등)로 옵션 A의 완화책만으로 충분한지 검증할 계획이 있는지
* 1인 개발 일정상 옵션 B/C의 학습곡선을 감수할 여유가 있는지

## 결과 (Consequences)
현재는 `system_architecture.md`/`tech_stack.md`상 Chat 서비스를 Spring Boot(서블릿) 기준으로 설계해두되, 옵션 A의 완화책(비동기 전송, 배치 코얼레싱, 방 단위 샤딩 등)은 어떤 프레임워크를 최종 채택하든 유효한 설계 원칙이므로 별도로 유지한다.
